I is the **modernization** tranche, governed by one spine — **the leverage principle**:

> glass-ui is the shared design system. An adoption that lands in `glass-ui/src` propagates to every consumer (fourier, value.js, words, speedtest, keyframes-demo, bbnf-buddy) at once. Therefore glass-ui-rooted waves rank highest, and within them the *substrate* fixes (overlay positioning, transform discipline) rank above leaf fixes.

It honors the established discipline: **token-bridged** (consume `--radius-*`/`--scale-*`/`--spring-*`, no literals — style-audit Axis 1), **no-legacy** (no `@supports`-fallback cruft beyond the gate the guide itself prescribes; `feedback_no_fallbacks`), **no-codegen** (inv-26 hand-typed-canonical), and **inv-16′** (every cross-repo write is its own commit, booked to an `ADOPTION-ASKS` entry, gated on that repo's own green CI). ## §2 — Invariants

I inherits all prior invariants (`docs/tranches/INVARIANTS.md`, inv-1…28 + the named C/F/G/H additions, incl. inv-16′) unchanged. I adds **two by name**, continuing the clean fresh-integer sequence (G 25/26, H 27/28, I 29/30):

- **inv-29 — progressive-enhancement-floor**: a modern-platform-API adoption ships **behind an `@supports`/feature gate with the prior path retained as the floor**. The modern path is the *enhancement*, not a replacement that breaks a non-supporting engine — Safari/Firefox parity is mandatory; there is NO rip-out of the working path. Concretely: anchor positioning (β), View Transitions (ε), scroll-driven animation (δ), `appearance: base-select` (η) each land behind `@supports` (or the framework equivalent — Vue-Router `viewTransition`) with the reka/`@floating-ui`/JS-listener/JS-combobox path as the `@supports`-false floor. Rationale: the audited surfaces serve real Safari/Firefox traffic; a native-only adoption that degrades on a non-supporting engine is a regression, not a modernization. Testable gate: every wave that names a recently-native capability cites both the `@supports` condition AND the floor it preserves; an `@supports`-false engine renders the prior path. *(Distinct from `feedback_no_fallbacks`/no-legacy: inv-29 sanctions exactly the ONE gate the guide prescribes — the progressive-enhancement bracket — and forbids fallback cruft BEYOND it; the floor is the working prior path, not manufactured `@supports`-fallback scaffolding.)*
- **inv-30 — platform-over-library**: prefer a native platform capability over a JS/library reimplementation **where the platform now suffices**. The library/JS path demotes to the `@supports`-false floor (inv-29) or is retired only when the platform is **universally** sufficient. This is the modern-web analog of inv-15 (no-library-nobody-calls): a reimplementation the platform has subsumed earns its keep only by its *residual differentiator*, not by inertia. Concretely: `@floating-ui`/reka positioning demotes to the floor under β (the platform does flip/shift/arrow); the three FLIP engines (speedtest `useCompletionChoreography`, keyframes `ElementMorph`-for-DOM, fourier's remount-flash) retire to View Transitions under ε; keyframes.js's `ScrollTimeline`/`ElementMorph` DOM-element paths recommend native under δ/ε — but its **true differentiators survive and are unique** (it *emits* the `linear()` spring stops glass-ui's `--spring-*` tokens are regenerated from; it animates off-DOM/non-element data on scroll, which `animation-timeline` cannot; WAAPI delegation with a real eligibility gate). **Verdict for keyframes: keep the engine, narrow the DOM-element public API to native, keep the off-DOM/spring-emission core** (keyframes-O1/O2/O3 — a narrowed remit, NOT a deprecation). Rationale: a library that reimplements a now-native capability adds maintenance + bytes for no platform-uncovered value; demoting it to the floor is the modernization, retiring it is premature until the platform is universal. Testable gate: each demotion names the native capability that subsumes it, the residual differentiator (if any), and whether the library is floored or retired.

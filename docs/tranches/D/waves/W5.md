## §1 — The ROOT (verified against the live live tree at HEAD `1e47115` + value.js HEAD `16129e0`)

### §1.1 — The live cross-repo `palette_slug` FK

`api/models/visualization.py:119` declares `palette_slug: str | None` — a **dangling slug-FK into value.js's palette noun**. A `visualization` can reference a `palette` by slug. The reference is *unvalidated string* today (no cross-service resolve call at write-time). value.js's `palette-api` (deployed `palette-api-api-1`, HTTP 200, 2 months live) serves `GET /palettes/:slug` (`value.js/api/src/routes/palettes/crud.ts:60-64 getPaletteBySlug` → `services/palette/crud.ts:44-61`). **This is the concrete reason cohesion matters**: the two nouns are *already linked by slug* in fourier's schema; the contract's "one identity model" is not academic, it is how a fourier visualization points at a value.js palette.

**The `palette_slug` FK contract** (new §clause in v2.0.0):

- **Fourier guarantees** (the writing side): `visualization.palette_slug` is stored as a non-empty validated slug (matching the slug shape §2 binds in v2.0.0 — `^[a-z0-9][a-z0-9-]*$ ≤ 120` chars, the relaxed form); never as a hash, never as a URL substring; never as the `palette.id` top-level field value.js currently emits (which v2.0.0 §1 forbids). The reference is *opaque-by-slug* — fourier does NOT validate the slug exists on the value.js side at write-time (no cross-service call; the eventual-consistency hand-off lives at read-time).
- **Value.js guarantees** (the resolving side): `GET /palettes/:slug` stays the slug-addressable read path; the slug is the lookup key (no `_id`-or-`id` parallel lookup); the slug remains the *one* user-facing handle for the palette noun (no second URL form via `id`). Soft-delete semantics (when v2.0.0 §5 lands on value.js's side): a soft-deleted palette returns 410 Gone (not 404) to make the FK-dangling-by-deletion case distinguishable from never-existed.
- **The frontier**: how fourier handles a 404/410 on `GET /palettes/:slug`. **The contract binds the *shape*, not the *resolution*** — fourier's product surface chooses how to render an unresolvable palette (e.g. fallback to the default palette; surface a warning; hide the swatch). No cross-service write-time validation; the FK is *opaque* by design (KISS — invariant 12).

### §1.2 — The two KISS relaxations (per `D/coordination/CRUD-COHESION.md §3`)

The B-era `CRUD-CONTRACT.md §2` and `§0` were authored *fourier-unilaterally* (B closed without value.js's joint ratification — `CRUD-CONTRACT.md:76-83`). Two clauses over-fit fourier's accidents; v2.0.0 relaxes:

**Relaxation 1 (§2 — user-supplied slugs are first-class).** v1.0.0 §2 demanded `^[a-z]+(-[a-z]+){3}$` (4 lowercase words, server-generated, cryptographic RNG, insert-then-catch retry). This is fourier's `coolname`-derived accident. value.js's palettes are **deliberately user-named** (the create body carries `slug`; `value.js/api/src/validation/palette.ts:41-46`). v2.0.0 §2 binds *uniqueness + shape-floor + insert-then-catch* — the slug is unique, matches a permissive shape (`^[a-z0-9][a-z0-9-]*$ ≤ 120 chars` — the value.js shape; subsumes fourier's tighter form), is generated server-side OR validated server-side from a user-supplied value, and the unique-key collision is handled by insert-then-catch retry (≤ 10 attempts for server-generated, single attempt for user-supplied with a `409 Conflict` problem+json on collision). **Server-generation remains REQUIRED for the anonymous/auto-creation path** (fourier's visualization create-from-extracted-contour flow — no human is naming it). User-supplied slugs are admitted for explicit naming flows (value.js's "name your palette" UX). Both modes pass the shape-floor and the insert-then-catch unique-key check.

**Relaxation 2 (§0 — behaviour binding, not module layout).** v1.0.0 §0 implied a shared *shape* (the `api/lib/crud/` 8-file utility-module layout fourier landed; `value.js/api/src/crud/` planned but never built — `DA3 §1` "ORPHANED-BY-PARALLEL-EVOLUTION"). v2.0.0 §0 binds **the observable CRUD behaviour** — `application/problem+json` error envelopes per RFC 9457, `ETag`/`If-Match` headers + 412 Precondition Failed per RFC 9110, `RateLimit-*` headers per RFC 9239, `Idempotency-Key` header on POST per the IETF draft, `Link: rel="next"` per RFC 8288 — **not the module layout that produces them**. value.js implements them in its `service + repository + errors + events + DI` idiom (the D.W2 architecture, `626b107`, won by parallel evolution per `DA3 §1`); fourier implements them in `api/lib/crud/`. The contract is **agnostic** to which file holds which utility; the assertion is "a `GET` returns an `ETag`; a `PATCH` without `If-Match` returns 428 Precondition Required; etc." Each clause in v2.0.0 §0 carries: (a) the behaviour binding (the wire-level assertion); (b) the SOTA citation (RFC#); (c) **NO module-layout prescription**.

### §2.2 — `§2` slug clause amendment

The v1.0.0 §2 text reads "`^[a-z]+(-[a-z]+){3}$`, 4 lowercase words, server-side cryptographic-RNG generation, insert-then-catch DuplicateKeyError retry ≤ 10". v2.0.0 §2 generalises:

> **§2 — Slug identity (v2.0.0).** Each entity is identified by exactly one user-facing handle, the *slug*. The slug satisfies the shape-floor `^[a-z0-9][a-z0-9-]*$`, length ≤ 120 chars; both repos MAY enforce a tighter local shape (fourier's `^[a-z]+(-[a-z]+){3}$` is one valid tightening). The content-hash and Mongo `_id` are NEVER user-facing identity (§1.3).

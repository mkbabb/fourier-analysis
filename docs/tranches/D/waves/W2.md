> **AMENDMENT (Wα-Δ-R4.1, 2026-05-27) — ACME challenge mechanism = HTTP-01 via `--apache`, NOT DNS-01.** The Wα-R4 live re-probe confirmed the host's certbot install does NOT carry the `dns-cloudflare` plugin (only `apache`/`dns-route53`/`standalone`/`webroot`). The binding `certbot --expand` invocation for this wave is therefore:
>
> ```bash
> sudo certbot --expand --cert-name sudoku.babb.dev \
>     --apache \
>     -d sudoku.babb.dev,fourier.babb.dev,words.babb.dev,api.fourier.babb.dev
> ```
>
> The `api.fourier.babb.dev` HTTP-01 challenge is served by the origin Apache directly (grey-cloud means CF returns the origin IP; LE hits `http://api.fourier.babb.dev/.well-known/acme-challenge/<token>` and Apache responds). The `cloudflare.ini` credentials file is **NOT created** at W2; the CF token's `Zone:DNS:Edit` perm is still used by the W8 DNS-as-code script but NOT by certbot. References below in §2.2 / §3.1 / §4 to `--dns-cloudflare`, `--dns-cloudflare-credentials`, `cloudflare.ini`, and DNS-01 mechanics are **superseded** by this amendment — they remain as documented Path A for future use (e.g. wildcard certs). The substantive cert chain, SAN set, vhost, CORS, and client-base outcomes are unchanged; only the ACME challenge mechanism changes. See `coordination/CONSTELLATION-DEPLOY.md §3.2.a` for the resolution.

The wave's two spines:

- **Spine 1 (provision-then-flags, inversion forbidden — inherited from `C/infra/tls.md §9`)**: the W2 cert provisioning runs **first** (the host `gen-mongo-certs.sh` re-issues the CA + leaf under `CN=fourier-internal-ca` with the four mandatory SANs); a live `db.runCommand('ping')` from the backend container with `tlsCAFile` + **no** invalid-cert flag passes; **only then** are the three `tlsAllowInvalid*` / `--tlsAllowConnectionsWithoutCertificates` flags removed from `docker-compose.prod.yml`, the backend CA mount is added, and the stack is restarted via the W1-deploy-hook. Removing the flags before the live cert + the live ping is the SAN footgun (`tls.md §3` + `R-tls-spec.md §6.6`) — the connection breaks the instant a permissive flag drops against an unknown-SAN cert.

- **Spine 2 (DNS-then-cert-then-vhost-then-client, also inversion-forbidden)**: the fourier domain split lands in dependency order — (a) DNS for `api.fourier.babb.dev` (grey-cloud A → origin `34.197.214.67`); (b) `certbot --expand` adds the SAN to the live LE cert via DNS-01; (c) the Apache vhost for `api.fourier.babb.dev` lands, the cert's new SAN coverage matches; (d) the backend's `CORS_ORIGINS` is verified to allow `https://fourier.babb.dev` (already correct per `NA5 §2.3`); (e) the web client API base moves from same-origin `/api` to `https://api.fourier.babb.dev` via env var (Vite build picks it up — no code change). Inverting steps (b)→(c) means the vhost's `SSLCertificateFile` points at a cert whose SANs do not cover `api.fourier.babb.dev` (the `NA5 §1.4` blocker — currently the cert covers fourier/sudoku/words bare apexes, but not `api.fourier`); apache would serve the wrong cert and TLS would handshake-fail.

Both spines run within W2 (the precepts promotion is a third, post-flight axis); they interleave at the deploy-hook boundary (after Spine 1 lands the verified-TLS posture in the prod compose + after Spine 2 lands the Apache vhost, the W1-wired deploy-hook ships the compose changes through the chain in one cutover). The wave authors run them as two parallel agents with the spine ordering as the binding inner sequence per agent.

### §1.3 — The `COMPUTE_RATE_LIMIT` e2e harness (the 429-cascade root fix)

`api/config.py:23` declares `compute_rate_limit: int = 5` with a comment naming the e2e override expectation: `# Production default is conservative; dev/e2e raise it via COMPUTE_RATE_LIMIT since a full lifecycle run issues several compute calls in quick succession.` The expectation exists; the harness does not yet wire it. The fourier local e2e runs hit the 5/60s limiter on the third extract-contour call and cascade — 23 of 49 cases fail downstream because the canvas-never-appears timeout fires when the contour POST 429s.

**The wire** (the W6 binding):

- **`web/playwright.config.ts`** declares a `webServer` block that launches the backend (or expects an already-running backend per the existing `:8000` bind-mount) — extend to pass `COMPUTE_RATE_LIMIT=1000` in the spawned backend's env.
- **OR** if the test session already expects a pre-launched backend (the current local dev flow per `scripts/dev.sh`), document the env-set in the README / dev script (`scripts/dev.sh` already exists; a one-line `export COMPUTE_RATE_LIMIT=${COMPUTE_RATE_LIMIT:-1000}` for the e2e launch profile, OR a sister `scripts/e2e.sh` that sets the env before invoking).
- **The prod limiter STAYS at 5.** `api/config.py:23` is byte-identical pre/post-W6. The only override site is the e2e launch env — the prod Docker image does NOT pass `COMPUTE_RATE_LIMIT`, so `Settings()` resolves the `5` default.

**Sub-gate**: `git diff HEAD -- api/config.py` returns empty (no production-config change); the e2e env raises the limit via the env var, never the config.

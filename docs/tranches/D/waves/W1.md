## §1 — The two-phase spine (Phase 1 BEFORE Phase 2 — inversion forbidden)

The user's binding direction (`D.md §3` W1 row; `CONSTELLATION-DEPLOY §3.1`, "**This is a live exposure that arguably warrants a hotfix ahead of the full tranche**"; PROGRESS §"resolutions folded", "Mongo fix in-tranche, front-loaded as the FIRST act of W1"): close the live world-reachable Mongo exposure across the shared host **before** any deploy operation runs. The reasoning:

- The exposure is **live and severe** (`NA5 §3.1` — three Mongos on `0.0.0.0`, UFW-opened, externally TCP-confirmed at `34.197.214.67:27017/27018/27020`, with the credentials in plaintext in the committed compose files — `cqC1rM9iGWw6xZoU5tFh4MqdQCvfvZBb`/`LkqzaB0NPF5nx4Wj1iCrUc5kxWYwra0W`, known to NA1 §4b). Every additional minute it stays open is risk. Phase 2 entails a non-trivial host operation (the FIRST gated deploy of A/B/C — the gate's failure mode is rollback, which is the bounded blast radius the wave is designed for), and a worst-case Phase 2 outcome (a partial-rollback regression, a transient app outage) is irrelevant to Phase 1's urgency — Phase 1 IS the urgent half. Doing Phase 2 first delays Phase 1.
- The two phases are **operationally independent**: Phase 1 changes the *host-network* publishing surface, not the *Mongo* container itself (the container stays running, the backend keeps reading `mongo:27017` over the compose-network bridge — `docker-compose.yml:19`-style — which is unaffected by `ports:` changes); Phase 2 changes the *fourier compose stack* (a deploy that rebuilds the fourier images). Doing Phase 1 first means Phase 2 lands on a host that is already in the post-Phase-1 posture, which is the steady-state target.
- The phases are paired on the **TLS attack surface** but separated by the wave boundary: W1 closes the *network-layer* exposure (loopback bind + UFW); W2 closes the *transport-layer* trust laxity (the three `tlsAllowInvalid*` flags); together they restore defence-in-depth on the prod DB surface. Closing the network half in W1 means the TLS-laxity flags in W2 are merely defence-in-depth, not the only defence — the right posture for an inter-wave hand-off. (`NA5 §3.2` — "Defence-in-depth pairing: combine the loopback/no-publish fix with C.W2's TLS cutover".)

**Inversion is forbidden.** No Phase 2 step lands before all of Phase 1 closes green and the operator-confirms-healthy gate (criterion 2) passes. If Phase 1 surfaces a co-tenant regression (floridify or palette degrades after its Mongo bind change), Phase 2 does not start — the regression is reconciled first; the wave's recovery model is "revert the offending compose edit; rerun the operator-confirms gate; only then proceed". Conversely, no Phase 2 step touches the Mongo bind or UFW state — that is Phase 1's domain only.

### §2.4 — UFW rule withdrawal (cross-app — shared firewall)

Per `NA5 §3.1` the UFW state carries four `ALLOW IN Anywhere` Mongo rules:

```
27017/tcp  ALLOW IN  Anywhere  # MongoDB - fourier-analysis
27018/tcp  ALLOW IN  Anywhere  # MongoDB - floridify
27019/tcp  ALLOW IN  Anywhere  # MongoDB - speedtest    (stale — no listener)
27020/tcp  ALLOW IN  Anywhere  # MongoDB - palette-api
   (+ identical v6 mirror rules)
```

Withdraw all four (the `:27019` is stale per `NA5 §3.1` — there is no mongo listener on it; the rule is leftover from a retired speedtest mongo). The operator runs (with `sudo`):

```
sudo ufw delete allow 27017/tcp
sudo ufw delete allow 27018/tcp
sudo ufw delete allow 27019/tcp
sudo ufw delete allow 27020/tcp
# (and the v6 mirrors, per `ufw status numbered` output — each rule has a paired v6 entry)
```

UFW's default-deny posture (`Default: deny (incoming)`) then governs the four ports — without an explicit allow, ingress is dropped. The `nft INPUT policy drop` (`NA5 §3.1`) is the underlying mechanism. This is the second half of the §2.1-2.3 fix — without it, a future re-publish silently re-exposes; the rule withdrawal is the durable mechanical guard.

**Pass criterion**: `sudo ufw status verbose` returns zero lines matching `2701[0-9]/tcp` or `2702[0-9]/tcp`; an external `nc -zv 34.197.214.67 27017 27018 27019 27020` returns "Connection refused" on all four (the proof-of-closure). Capture the transcript.

## §6 — Migration-with-deploy: the placement decision

The invariant `D.md §2` "code-and-migration cut over together" requires that `python -m api.scripts.migrate_image_blobs` runs in the same cutover as the W5 serving code. The placement decision:

**Option A — invoke from `scripts/deploy-hook.sh`** (the canonical, recommended path):

After `build_and_up` (`deploy-hook.sh:137-138`) and before `health_gate` (`:140-141`), insert:

```bash
log "running migrate_image_blobs (code+migration atomic; D.md §2 invariant)..."
"${COMPOSE[@]}" exec -T backend python -m api.scripts.migrate_image_blobs 2>&1 | tee -a /opt/deploy/logs/migrate-$(date -u +%Y%m%d-%H%M%S).log
local mig_rc=${PIPESTATUS[0]}
if (( mig_rc != 0 )); then
    log "migration FAILED (exit ${mig_rc}); rolling back without further gating"
    git reset --hard "${prev}"
    build_and_up
    return 1
fi
```

This binds the migration to the deploy chain — if the migration fails, the deploy fails (and rolls back). The migration's idempotency (`migrate_image_blobs.py` docstring lines 21-25) means a re-run after the rollback is safe — the field-flip marker (`storage_uri` presence) prevents double-processing. The empty-DB no-op character means the W1 invocation logs zero work but exercises the integration path. **Pass criterion**: `grep -E 'migrate_image_blobs|MIGRATION' /opt/deploy/logs/mkbabb-fourier-analysis-*.log` shows the invocation; the migration log shows `relocated=0 skipped=0`.

**Option B — invoke externally, post-deploy**:

Run `docker compose exec backend python -m api.scripts.migrate_image_blobs` as a one-shot after the deploy-hook returns GREEN. Rejected: the invariant says "in the same cutover" — running it externally is not the same cutover, and the discipline that protects against "environment runs code ahead of migration" (`D.md §2` testable gate) is the deploy-hook's atomicity. Option A is the binding choice.

**Pass criterion**: the deploy-hook log shows the migration invocation between build and health-gate; the migration's exit code is captured in the log; on a no-op run the exit code is 0; on a future non-empty DB run, a non-zero migration exit triggers the rollback path.

D.W1.b's repo-local file write therefore *includes* the `scripts/deploy-hook.sh` edit adding this hunk. The §4 D.W1.b mechanism is updated to "edit `scripts/deploy-hook.sh` per Option A; the edit ships in the W1 deploy and is exercised in the same deploy that lands it (the deploy-hook's own first-run is itself; the edit applies to the FIRST D-W1 deploy)". The bootstrap (§3.2) of the deploy-hook onto the host must use the post-edit version (the edited `scripts/deploy-hook.sh` from D-W1-HEAD, not master-as-of-C-W1-close), so the host bootstrap step is `git checkout <D-W1-HEAD-or-master-after-edit> -- scripts/deploy-hook.sh`.

## §1 — The reconciliation — provenance + rename target + scope boundary

The single sharpest finding (NA1 §5 + DOMAIN-NAMING §3 + NA4 §2.3): **prod's palette-api is rsync-deployed from a STANDALONE repo at `/home/mbabb/Programming/palette-api`, NOT a git checkout of `value.js/api/`**. - `api.color.babb.dev` already encodes the "api-ness" in the vhost (W10).
- Container names + the package name are best **single-word** for clarity in `docker ps` output, log lines, and `package.json` reads.
- **The recommended target is `color`** (the package, repo dir, compose project all match the frontend's CF Pages project name `color` from W9.c). **`color-api` is the rejected alternative** — it duplicates the `api.color.babb.dev` semantics and adds a hyphen for no gain.
- The npm library `@mkbabb/value.js` (the library qua library, `value.js/src/`) stays named `value.js`. The demo (`value.js/demo/{color-picker,hero-lab}`, which IS the `color.babb.dev` frontend, NA4 §2.4) stays named `value.js` in the demo's own package.json. Only the **backend service** (`palette-api`) renames.

NA6 §1(d) "**rename ONLY what the user named**": the user named the rename of the **palette-api endpoint to color** (DOMAIN-NAMING §1 quote). The scope boundary:

| Surface | Rename? | Reason |
|---|---|---|

### §2.3 — Mongo data continuity

The rename **MUST NOT** orphan Mongo data. The mongo container's volume is named in compose; renaming the compose project changes the volume's prefix (`palette-api_mongo-data` → `color_mongo-data` if compose-managed names). Two paths:
- (a) **Pre-rename**: take a `mongodump` of the live palette mongo (to a host-side snapshot).
- (b) **Volume reuse**: edit the new `compose.yaml` to declare the existing volume name as `external: true` referencing `palette-api_mongo-data` (or re-bind via `docker volume create color_mongo-data` after copying the prior volume content). This preserves the data without a restore step.

**Recommended** (per `D.md §3 W11` row): the simpler path — `mongodump` pre-rename, `mongorestore` post-rename (after the new `color-mongo-1` is up). The dump+restore is a 1–2 minute operation for the palette database size (the live container is healthy 2 mo; data is small). **W11 does NOT skip the data-continuity step**; the close gate requires the rename to land **with data preserved**.

### §2.4 — `palette-Mongo` loopback bind (W1 hold-over verification)

The W1 wave (front-loaded security per `D.md §3 W1`) bound all three Mongos off `0.0.0.0` — including `palette-api-mongo-1` (NA1 §1 + NA5 §3.1). W11 **verifies the bind held through the rename**:

- `ss -tlnp | grep 27020` shows `127.0.0.1:27020` only (or no listener at all if no-publish chosen).
- UFW has no `27020/tcp` ALLOW rule (W1 withdrew it).

W11 **does NOT re-bind** the Mongo (that was W1's act); it **verifies** the bind survived the rename. If the new compose.yaml regresses the bind to `0.0.0.0:27020`, W11 fails the gate; the operator restores the bind before W11 closes.

### §2.5 — CORS re-verification

W10 set `ALLOWED_ORIGINS=https://color.babb.dev` for palette-api. The rename should not regress this (the env is set in the host compose or `.env`). W11.b verifies:

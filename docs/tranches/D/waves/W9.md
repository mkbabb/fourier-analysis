## §1 — The reconciliation — pilot-then-rollout, binding sequence

The single sharpest argument (NA6 §4): **prove the full pattern on fourier first, end-to-end, on the live shared host, with W1/W2's backend side already in place — then mechanically replicate the recipe across the others, bounded-parallel.** The trap-to-reject (NA6 §1(b)) is **a custom build/deploy pipeline** — a hand-rolled artefact-uploader, a self-hosted runner orchestrating builds, a per-app divergent CI shape. The KISS verdict: **the speedtest/wrangler recipe is the single mechanism**; per-app peculiarities (fourier's precompute step) become **build steps inside the standard workflow**, never a pipeline fork.

The binding sequence — each step is a separate sub-wave that **cannot start until the previous verified green**:

```
W9.a  fourier-pilot              (W1/W2 done → CF Pages frontend + custom-domain attach → DNS flip)
  ↓   GATE: fourier.babb.dev returns 200 from CF + api.fourier.babb.dev preflight + GET green
W9.b  keyframes                  (GH-Pages teardown — verify on .pages.dev → flip DNS → retire peaceiris → delete gh-pages branch)
W9.c  value.js/color             (GH-Pages teardown — same shape as keyframes; the value.js repo)
W9.d  sudoku/csp-solver          (mbabb-nginx teardown — the apex serves from CF Pages; the gateway port stays for api.sudoku at W10)
  ↓   GATE: every in-scope app returns 200 from CF; the apex and api sides cleanly separated
W9.close  grammar disposition recorded as DEFERRED in PROGRESS.md
```

W9.b/W9.c/W9.d may overlap subject to the **3-concurrent cap** (NA6 §3.2 4-agent ceiling, minus one for the team-lead orchestration agent), provided W9.a closed first. The cap is **agents**, not **apps**: a single agent owning two apps' cutover is permitted (the GH-Pages teardown is identical for keyframes and value.js/color — a competent agent can drive both in one session). The ban is on **simultaneous-without-pilot** — no app starts until fourier-pilot verifies green.

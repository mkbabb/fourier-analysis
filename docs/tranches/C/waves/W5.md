## Goal criterion (paired)

**Goal.** Relocate the inline image-and-thumbnail `Binary` blobs out of each `images` document onto a bounded, observable, *reclaimable* filesystem backend (`blob_dir`, an app-writable named volume), recording `storage_uri` / `thumbnail_uri` on the owning document — with the inline-`blob` write deleted, the delete path coupled to the relocated bytes, and the serving endpoints re-pointed at the files via `FileResponse`. No dual-read layer survives the cutover (the per-document flip is atomic; invariant 3 forbids legacy code).

**Completion criterion.** W5 succeeds when:
1. `grep -n 'Binary(content)' api/services/image_storage.py` returns **zero** (the deletion proof — `image_storage.py:104` no longer writes the inline blob);
2. the migration ran with a recorded **count-parity artefact**, a **10-row byte-identity spot-check** green, and the **`blob` XOR `storage_uri` post-condition** asserted (no doc carries both; none carries neither);
3. the janitor image-delete **unlinks** `<blob_dir>/<slug>` + `<slug>.thumb` (C1), proven by a delete-then-assert-file-gone test;
4. the dedup-hit-on-migrated-doc path is rewritten through the shim and writes its thumbnail **as a file + `thumbnail_uri`** (never an inline `Binary`), proven by `test_dedup_hit_on_migrated_doc` (C9);
5. the volume is app-writable (C2), `_resolve()` is path-confined (C3), the backfill projection no longer starves the shim (C10), no skip-if-exists short-circuit exists (C11);
6. `…/blob` + `…/thumbnail` serve via `FileResponse` with route + auth + `Cache-Control` + the `last_accessed_at` touch unchanged;
7. the backup/DR note + `external:true` volume protection land (C4);
8. `uv run pytest` green (the inherited suite + the new `api/tests/test_migrate_image_blobs.py`).

Every C1–C12 gate in §Hard-gate ledger holds, each as a provable grep / test / assert.

## Sequenced steps

The steps below are ordered by dependency. Steps 1–3 are the *substrate* (config → volume → migration script); step 4 is the **single deletion-proof commit** that flips the live write/read/delete paths; step 5 re-points serving; step 6 lands the DR note. Steps 1–3 may land in their own commits (they do not break the live path — the inline `blob` write still serves until step 4); step 4 is atomic.

### Step 1 — config: `blob_dir`

Add one field to `Settings` (`api/config.py`), mirroring `max_upload_mb` (`config.py:11`):

```python
blob_dir: str = "/data/blobs"   # filesystem backend root; volume mount point in prod
```

No index change (`R-storage-spec §1.1` — relocation is keyed by `image_slug`, already unique-indexed at `database.py:50`; `storage_uri` is never queried).

### Step 2 — volume add + ownership (C2 — BLOCKER)

The named volume + its app-writability. Three facts ground the ownership break (`challenge-P1.md §3`): the prod backend runs as the unprivileged `app` user (`api/Dockerfile:19` `adduser --disabled-password app`; `:23` `USER app`); the only `chown` in the image is `:21` `RUN chown -R app:app /app/.venv` — scoped to the venv, **not** to any data path; a fresh named Docker volume is created **root-owned** by the daemon. So `_blob_dir().mkdir()` and every `write_bytes` raise `PermissionError: [Errno 13]` as `app` against a `root:root` mount — the migration aborts on the first write and every upload 500s. This is `mongo_data`'s posture NOT transferring: only the `mongo` container (its own user) writes `/data/db`; `image_blobs` is the **first** volume the unprivileged `app` user must write to (`challenge-P1.md §3`).

- `docker-compose.yml` (base — invoked first in the `-f docker-compose.yml -f docker-compose.prod.yml` merge, `scripts/deploy.sh:26,29`): add the named volume to the top-level `volumes:` block (today `volumes: [mongo_data]` at `docker-compose.yml:50-51`) → add `image_blobs:`. Mount it into `backend` (today `docker-compose.yml:8-11` declares only the source bind-mounts) → add `image_blobs:/data/blobs` (or a dev bind-mount for dev parity, `R-storage-spec §1.2`).
- `docker-compose.prod.yml` `backend` block (`:2-19`, declares **no** `volumes:` today): add `volumes: ["image_blobs:/data/blobs"]` (read-write).
- **Establish ownership** by ONE of (W5 picks at dispatch, confirming the `app` UID from `api/Dockerfile:19`):
  - a compose `user:` directive on `backend` matching the volume owner; OR
  - an entrypoint / init `chown` of `blob_dir` to the `app` UID before the server starts; OR
  - a pre-ownership step on the named volume.
  The chosen mechanism is the C2 gate: the migration + an upload must succeed as `app` (no EACCES).

### Step 3 — migration script (per `R-storage-spec §3`)

Create `api/scripts/migrate_image_blobs.py`, mirroring `api/scripts/migrate_visualization.py` exactly (the in-tree idiom: `--dry-run` + live, `Report` dataclass, post-condition asserts, count-parity, idempotent-by-marker, standalone-non-`--reload`, no-dual-read). Per `R-storage-spec §3.1–§3.2`:

- **Idempotent by DB marker.** Select only `find({"blob": {"$exists": True}, "storage_uri": {"$exists": False}})` — a converged re-run is a total no-op. The marker is the **field flip** (`storage_uri` presence), never file existence (C11, below).
- **Per-doc three-step cutover** (`R-storage-spec §3.1`, §4): (1) read `blob` (+ `thumbnail`) bytes already in Mongo; (2) `write_bytes` the file(s) to `<blob_dir>/<slug>` (+ `<slug>.thumb`); (3) ONE atomic `update_one({$set: storage_uri/thumbnail_uri}, {$unset: blob/thumbnail})`. Step 2 precedes step 3, so a flipped doc's file provably exists; step 3 is a single-doc atomic op, so `blob` XOR `storage_uri` holds at every instant.
- **`thumbnail_uri = None`** when the doc never had a thumbnail (the `_generate_thumbnail` except path can leave none, `image_storage.py:88,95-96`) — the `null` is recorded, not omitted.
- **Count-parity** (`assert_count_parity`): `images_before == relocated + skipped_already_migrated`.
- **Post-conditions** (`_assert_post_conditions`, RuntimeError on any): (a) zero docs with BOTH `blob` and `storage_uri`; (b) zero docs lacking `storage_uri`; (c) zero docs retaining an inline `thumbnail` Binary — the **blob-XOR-uri post-condition**.
- **10-row byte-identity spot-check** (`R-storage-spec §3.2`): a separate verification pass BEFORE the deletion-proof commit lands, against 10 sampled docs — read the file at `<blob_dir>/<slug>` and assert its bytes `==` the bytes the doc's `blob` held. The harness fails unless all 10 are byte-identical. (The seed=42 / 10-row discipline mirrors `migrate_visualization.py:72-73`.)
- **C11 — NO "skip if file exists" short-circuit.** `Path.write_bytes` is non-atomic (`open("wb")`→`write`→`close`); a crash mid-write leaves a truncated partial file. The self-heal rests entirely on the re-run re-issuing a truncate-and-overwrite `write_bytes` against any doc still matching `{blob exists, storage_uri absent}` (`challenge-P3.md §4`). A "skip if file present" optimization would skip the truncated partial **permanently** → corruption. The idempotency marker MUST stay the field flip. *(Hardening option, not a blocker: write-temp + `os.replace` for no-partial-file-ever-observable semantics, `challenge-P3.md §4 (3)`.)*

The conformance suite (`R-storage-spec §3.2`): `api/tests/test_migrate_image_blobs.py::{test_idempotent_re_run, test_post_condition_blob_xor_uri, test_completeness_count_parity, test_spot_check_byte_identity}` (plus the C9/C10 tests below).

### Step 4 — THE DELETION-PROOF COMMIT (one commit; C9+C10+C1+C3 land here)

In the **single commit** that proves the migration ran (count-parity artefact + green harness), all six edits land together so no live span has the cutover code present while a consumer reads a phantom `blob` (`challenge-P3.md §5`):

1. **Delete the `:104` Binary write.** `image_storage.py:104` `"blob": Binary(content)` is removed; `store_image_asset`'s insert (`:99-108`) instead `write_bytes`-es the file(s) to `blob_dir` and sets `storage_uri`/`thumbnail_uri` (both blobs — primary at `:104`, thumbnail relocated from the `:91-94` `thumbnail_fields`/`:92` `Binary(thumb_bytes)`). No inline `blob` or `thumbnail` Binary is written on insert. → `grep 'Binary(content)'` returns zero.
2. **Delete the `image_bytes` blob-read branch.** `image_bytes` (`image_storage.py:139-143`) currently reads `asset["blob"]` unconditionally (`:141`). Rewrite it to resolve by `storage_uri`-presence (`R-storage-spec §2.1`): `uri = asset.get("storage_uri"); if uri: return _resolve(uri).read_bytes(), content_type`. The `blob`-reading branch is **deleted** post-cutover — no doc carries `blob`, so a surviving `blob` read would be the dual-read legacy layer invariant 3 forbids (`R-storage-spec §2.1` NO-legacy clause). The atomicity (§4) is what makes the deletion safe.
3. **Rewrite the dedup-hit path (C9 — the real bug).** `store_image_asset`'s sha256-dedup branch (`image_storage.py:66-85`) reads `existing["blob"]` as a **subscript** (`:70-72`) to regenerate a thumbnail → `KeyError` on a migrated (`blob`-less) doc → **swallowed by the broad `except Exception` at `:81`** → silent missing-thumbnail regression (it returns `existing` at `:85` with no surfaced error). It fires on *every* dedup upload after migration and has **zero test coverage** (`challenge-P3.md §2`). Worse, the write-back at `:75-80` (`:77` `Binary(thumb_bytes)`) **re-inlines a thumbnail Binary** — re-violating invariant 18 on the converged collection. Rewrite BOTH halves:
   - **(a) READ** the bytes through the `image_bytes` shim (the relocated file), not `existing["blob"]`;
   - **(b) WRITE-BACK** the regenerated thumbnail to `<blob_dir>/<slug>.thumb` and `$set thumbnail_uri`, **never** `$set thumbnail: Binary(...)`.
   Prove with `test_dedup_hit_on_migrated_doc` (`R-storage-spec §3.2`): a dedup upload onto a `storage_uri`-only doc regenerates the thumbnail **from the file** and re-records `thumbnail_uri` (not `thumbnail`).
4. **Change the backfill projection (C10).** `_backfill_image_bounds` (`dependencies.py:87-130`) projects `{"blob": 1, "content_type": 1}` (`:93`, inclusion-mode) then reads `image_doc["blob"]` (`:99`, subscript). On a migrated doc the projection returns no `blob` AND no `storage_uri` (inclusion-mode starves the shim), so even the shim cannot rescue it → `KeyError` → swallowed by the `try/except` at `:98/:125-128` → overlay alignment silently degrades (`challenge-P3.md §3`). Change the **projection** at `:93` to include `storage_uri`/`thumbnail_uri`/`content_type` (or drop the projection) AND the read at `:99` to go through the shim. Add `test_backfill_image_bounds_on_migrated_image`.
5. **Add the janitor unlink (C1 — BLOCKER, inv-18 delete-coupling).** `_delete_images_and_cascade` (`janitor.py:251-274`) today collects slugs (`:257-259`), cascades to `db.gallery` (`:265`), then `db.images.delete_many(filter_)` (`:273`) — it deletes Mongo docs and **nothing else**. Post-W5 the bytes are NOT the document, so a pruned doc's files at `<blob_dir>/<slug>` + `<slug>.thumb` are never unlinked → the volume grows monotonically, the bounded-footprint enumeration query lies, and invariant 18 is **defeated by the fix** (`challenge-P1.md §2`). Extend the function to unlink `<blob_dir>/<slug>` and `<blob_dir>/<slug>.thumb` (best-effort — a missing file is not an error, the crash-orphan re-run may have left none) for every slug in `slugs_to_delete`, in the same cascade, BEFORE or alongside the `delete_many`. This is the **sole** image-delete site in the tree (the `admin.py` `delete_many` calls target `flags`/`visualizations`/`sessions`/`users`/`gallery`, never `images`; `admin.py:145` is an aggregate, not a delete — confirmed). Prove with a delete-then-assert-file-gone test (`C.md §6`).
6. **Add the `_resolve` guard (C3 — hardening).** The `_resolve(uri)` helper (`R-storage-spec §2.1`, new in `image_storage.py`) parses `"fs:<slug>"` → `<blob_dir>/<slug>` and MUST assert confinement: `path = (Path(blob_dir) / key).resolve(); assert path.is_relative_to(Path(blob_dir).resolve())`. The slug regex (`IMAGE_SLUG_PATTERN`, `dependencies.py:38`, class `[-a-zA-Z0-9]`, no `.`/`/`/`%2e`) blocks traversal at the edge *today* (`challenge-P1.md §5.1`), so this is **not a live hole** — it is the second layer that keeps a future less-validated `storage_uri` writer from becoming an arbitrary-read. Two lines.

### Step 5 — `FileResponse` serving

`images.py` `…/blob` (`:132-140`) + `…/thumbnail` (`:143-156`): replace `StreamingResponse(io.BytesIO(data), …)` with `FileResponse(path, media_type=content_type, headers={"Cache-Control": "public, max-age=86400"})`. `FileResponse` streams from disk with `Content-Length` + conditional-request support, strictly better than the in-memory `BytesIO` for large blobs (`challenge-P1.md §5.4`). **Unchanged**: the route, the `get_image_asset` dependency (404 + the `touch_document` access-time touch, `dependencies.py:47-55`), the `Cache-Control` header, and the `last_accessed_at` touch the recency prune depends on (`janitor.py:99-102`; `R-storage-spec §2.2,§2.3`). The `…/thumbnail` `null`-thumbnail fallback to the primary `storage_uri` (today `images.py:147-151`) is preserved. The `…/overlay` path (`images.py:159-200`, reads `image_bytes` at `:169`) is **already shim-routed** — C12, confirmed, no extra work, listed so it is not forgotten (`challenge.md §3 C12`).

### Step 6 — backup/DR note (C4)

Create `docs/precepts/infra/` (does not exist yet) with the backup/DR note. Post-cutover the volume holds the **sole copy** of user uploads (the inline `blob` is `$unset`, `R-storage-spec §3.3`), and `image_blobs` is a **second independent durable surface** that must be backed up *consistently* with `mongo_data` — a `mongo_data` snapshot at T1 + an `image_blobs` snapshot at T2 can restore a doc whose `storage_uri` points at an absent file, or orphan files whose doc the Mongo snapshot lost (split-brain-on-restore, `challenge-P1.md §4`). There is **no** `mongodump`/backup mechanism in the tree today (`challenge-P1.md §4` — verified absent), so the note states the consistency requirement, not a "one added line." Additionally: declare the prod `image_blobs` volume **`external: true`** (in the base `docker-compose.yml` top-level `volumes:` block, or the prod overlay) so `docker compose down -v` cannot wipe the only copy — the cheap mechanical guard (`challenge-P1.md §4,§6`; `challenge.md §1 C4`).

## Summary

W5 relocates the inline image+thumbnail `Binary` blobs onto an app-writable `blob_dir` named volume (C2 — root-owned-by-default would EACCES the unprivileged `app` user, `Dockerfile:19,21,23`), recording `storage_uri`/`thumbnail_uri` per document. The **deletion-proof commit** lands six edits in ONE commit: delete the `image_storage.py:104` `Binary(content)` write; delete the `image_bytes` blob-read branch (no surviving dual-read, invariant 3); rewrite the C9 dedup-hit path to read through the shim AND write its thumbnail as a file + `thumbnail_uri` (never an inline `Binary` — the `:77` re-inlining was the silent invariant-18 re-violation); change the C10 backfill projection off `{blob:1}`; add the C1 janitor unlink in `_delete_images_and_cascade` (the sole image-delete site); add the C3 `_resolve` confinement guard. The **C9 dedup-bug** fix closes a real runtime regression: `existing["blob"]` (`image_storage.py:70-72`) KeyErrored on a migrated doc, swallowed by the broad `except` at `:81`, silently dropping the thumbnail, with zero prior test coverage.

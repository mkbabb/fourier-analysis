## Goal criterion

This wave succeeds if the MongoDB production trust posture becomes **verified server-only TLS** — full chain validation against a mounted, recorded self-signed internal CA plus hostname/SAN match — discharged by *removing* the three `tlsAllowInvalid*`-family flags rather than by adding a permissive knob (`R-tls-spec.md §1`). The discharge is gated on a **cert re-provisioning step that runs first**: the existing `/etc/ssl/mongo.pem` provenance is unknown from the tree (`W0-baseline.md §1.2`: "cert provenance … is unknown … an invariant-19 'verified-cert issuer recorded' gate cannot be met until the provenance is known"), so W2 re-issues the leaf under a recorded internal CA whose SANs cover every name a client uses to reach mongod, then removes the flags. The wave's **substrate-with-proof discipline** binds: the flag removal is only landed after a live `db.runCommand('ping')` from the app container — with `tlsCAFile` and **no** invalid-cert flag — succeeds against the re-provisioned cert. The invariant-19 close gate (`C.md §6`: "no `tlsAllowInvalidCertificates` (all three sites); the verified cert issuer is recorded in `docs/precepts/infra/`") closes only when the issuer line `CN=fourier-internal-ca` lands in `docs/precepts/infra/tls.md` (`R-tls-spec.md §4`: "'TLS enabled' without a verified-cert issuer is a named invalid gate").

## The spine — provision-then-flags, in that order (the R3 W2 pre-condition)

This is the load-bearing sequencing constraint of the entire wave. **The cert provisioning MUST complete before any flag removal**, or the connection breaks the instant the permissive flag is dropped against a cert whose SANs do not cover the connect-name (`R-tls-spec.md §2` "the W2 pre-condition"; `R-tls-spec.md §6.6` the SAN footgun; `R-tls-spec.md §0 Achievability` "the invariant-19 close gate is achievable in W2 conditioned on the §2 provisioning step running first — the existing undocumented certs cannot satisfy it"). The flags are the *only* thing currently letting the app connect to a cert of unknown SAN coverage; removing them before a SAN-correct cert is in place at `./ssl/mongo.pem` on the deploy host is an immediate outage.

The wave is therefore **two ordered phases gated by a live proof between them**:

```
  ┌─ STEP 1 — PROVISION ────────────────────────────────────────────────┐
  │  S1  generate / record the internal CA (CN=fourier-internal-ca)      │
  │  S2  issue the mongod leaf with SANs: mongo, localhost, 127.0.0.1,   │
  │        mbabb.fridayinstitute.net  → concat into mongo.pem            │
  │  S3  place mongo.pem (0600) + mongo-ca.pem (0644) in deploy ./ssl/   │
  └──────────────────────────────────────────────────────────────────────┘
                              │  GATE Gp (provision) — the SAN-footgun proof
                              ▼
  ┌─ STEP 2 — FLAGS ────────────────────────────────────────────────────┐
  │  S4  backend service: add  ./ssl/mongo-ca.pem:/etc/ssl/...:ro mount  │
  │  S5  site 1 (prod.yml:8):  drop tlsAllowInvalidCertificates,         │
  │        add  tlsCAFile=/etc/ssl/mongo-ca.pem                          │
  │  S6  site 2 (prod.yml:48): drop --tlsAllowConnectionsWithoutCert…    │
  │  S7  site 3 (prod.yml:53): healthcheck → --tlsCAFile /etc/ssl/...    │
  │  S8  site 4 (.env.example:21): tlsCAFile + host-spelling reconcile   │
  └──────────────────────────────────────────────────────────────────────┘
                              │  GATE Gf (flags) — live ping with CA, no flag
                              ▼
  ┌─ STEP 3 — RECORD ───────────────────────────────────────────────────┐
  │  S9  docs/precepts/infra/tls.md — issuer + SANs + procedure +        │
```

**Inversion is forbidden.** Any commit that removes a flag (S5/S6/S7) before Gp passes is a wave-spec violation; the orchestrator integration commit lands the flag drops only after Gp is green. The recording step (S9) may author in parallel with S1–S3 (it transcribes the procedure) but its close-gate evidence (Gr) cannot be claimed until S1 has produced the actual issuer string.

## Scope

Generate a self-signed internal CA (`openssl req -x509 … -subj "/O=fourier-analysis/OU=infra/CN=fourier-internal-ca"`, 4096-bit RSA / SHA-256 / 10-year root — `R-tls-spec.md §2.1`); issue the mongod server leaf with the **mandatory SAN set** `DNS:mongo`, `DNS:localhost`, `IP:127.0.0.1`, `DNS:mbabb.fridayinstitute.net` (`R-tls-spec.md §2.2`); concatenate `server.crt` + `server.key` into `mongo.pem`. **The `scripts/gen-mongo-certs.sh` option** (`R-tls-spec.md §4.4`): W2 may distill the §2 commands into a committed script — *the script is committed, the keys it emits are not*. `ca.key`, `server.key`, `mongo.pem` never enter the repo (`ssl/` stays gitignored at `.gitignore:79` — confirmed live). Only `mongo-ca.pem` (public) and the procedure are shareable. 2. **Site 1 — client URI + the backend CA mount** (S4–S5; `R-tls-spec.md §3.1`). At `docker-compose.prod.yml:8`, **delete** `tlsAllowInvalidCertificates=true` and **add** `tlsCAFile=/etc/ssl/mongo-ca.pem` to the `MONGO_URI` query string. pymongo 4.16 parses `tlsCAFile` as a URI query option; full verification (chain + the §2.2 SANs, which include `mongo`) then applies. **The CA must be mounted into the backend container** — it is currently mounted only into mongo (`:57-58`). The prod `backend` service declares **no `volumes`** today (`docker-compose.prod.yml:2-19`); W2 adds the single read-only CA mount `./ssl/mongo-ca.pem:/etc/ssl/mongo-ca.pem:ro`. The leaf `mongo.pem` is **not** mounted into the backend — server-only TLS, the client presents no cert (`R-tls-spec.md §3.1`).

3. **Site 2 — mongod server** (S6; `R-tls-spec.md §3.3`). At `docker-compose.prod.yml:48`, **delete** the line `"--tlsAllowConnectionsWithoutCertificates",`. Under SCRAM-only auth (no x509 client certificate) the flag is vacuous (`R-tls-spec.md §3.3`); certless SCRAM clients still connect. At `docker-compose.prod.yml:53`, replace `"--tls", "--tlsAllowInvalidCertificates",` with `"--tls", "--tlsCAFile", "/etc/ssl/mongo-ca.pem",`. mongosh runs inside the mongo container where `/etc/ssl/mongo-ca.pem` already exists (`:58`); the SAN `localhost`/`127.0.0.1` from §2.2 covers the in-container connect target. **No new mount needed** for the healthcheck.

## Triumvirate Dispatch

The triumvirate fires when the wave's file bounds, hard gate, or the provisioning contract no longer describes the work required to close. For W2 the trigger surfaces are:

The measured host facts vs. the spec's fiction:

| Live host fact (measured, read-only, `challenge-P2.md §1.1`) | Greenfield spec clause it falsifies |
|---|---|
| `webhook` binary `/usr/local/bin/webhook`, **service active** | `R-deploy-spec §3.1` "W1 installs" — already installed |
| `ExecStart=… -hooks /opt/deploy/hooks.json -port 9000 -verbose -hotreload` | spec hooks path `/etc/webhook/hooks.json` (`R-deploy-spec §2.2`) — live is **`/opt/deploy/hooks.json`** |

| `execute-command: /opt/deploy/scripts/dispatch.sh`, `command-working-directory: /opt/deploy` | spec "tracked in-repo `scripts/deploy-hook.sh`" (`R-deploy-spec §3.2`) — live logic is an **un-tracked host script** outside fourier's tree |

That is the invariant-19 HMAC model `R-deploy-spec §2` chose, and it is **already live**. The auth verdict is vindicated by reality; everything structural around it is wrong on the page.

**The mandate (`C.md §5.4`; synthesis `§2 C5`):** the greenfield `/etc/webhook/`+root-`0600`+loopback design is **REJECTED as a fiction**. ## §2 — Stratum A: repo-local, landable AND provable from this repo (the actual W1 deliverables)

These land in fourier's tree and prove from fourier's commit chain alone. They are the wave's binding deliverables.

### §2.1 — `scripts/deploy-hook.sh` (tracked, new) — the dispatcher's invocation contract, hardened

W1 authors a tracked `scripts/deploy-hook.sh`. It is written to **match the existing dispatcher's invocation contract** — the live `dispatch.sh`'s fourier `case` arm calls it (or is rewritten to call it) with `command-working-directory: /opt/deploy` and the GitHub `repository.full_name` passthrough — so the host can adopt it without re-architecting the shared receiver. But it carries the four improvements the live `dispatch.sh` provably lacks (measured at `challenge-P2.md §2.2`, `§3`):

1. **`flock` serialisation (the live dispatcher has NONE).** `grep -c flock` on the live `dispatch.sh` = 0 (`challenge-P2.md §3`). The script wraps its body in `flock /run/lock/fourier-deploy.lock` so overlapping fourier triggers serialise (the replay/two-rapid-push contract `R-deploy-spec §6` rows 3–4 leans on — unmet on the host today). The lock is **fourier-scoped** (a fourier-named lockfile), so it does not block sibling-repo deploys; cross-repo concurrent-build resource contention on the 15 GiB host (`challenge-P2.md §3`) is a shared-dispatcher concern named in Stratum B, not solvable from one repo's lockfile.

2. **A REAL `:8100` health-gate — sourced from `${HTTP_PORT:-8100}`, no swallow.** The gate polls `http://127.0.0.1:${HTTP_PORT:-8100}/api/health` expecting `{"status":"ok"}` (the live route, `api/main.py:125-127`) **and** `http://127.0.0.1:${HTTP_PORT:-8100}/` for the SPA. The port is sourced from `${HTTP_PORT:-8100}` — the *same default the compose nginx bind uses* (`docker-compose.prod.yml:72`, `127.0.0.1:${HTTP_PORT:-8100}:80`) — so the gate and the bind **cannot drift** (the structural fix for the `:8091` class of bug, `W0-baseline.md §1.1`). The gate is a **bounded poll** (≈60 s, ≈2 s interval) whose non-zero exit is **load-bearing** — it *is* the rollback trigger. There is **no `|| echo` swallow** (the `deploy.sh:38-39` defect — the curl falls through to `|| echo "not responding"`, so a dead port "passes"). This both retires the `:8091` bug (which curls the wrong port, `deploy.sh:38`) and removes the swallow that hid it.

3. **Rebuild-on-rollback (the live dispatcher does `up -d` ONLY — no rebuild, no re-gate).** The live `dispatch.sh` rollback (`challenge-P2.md §2.2`) does `git reset --hard "$PREV"` then `up -d` only — no `build`, no re-poll — so it restarts containers built from the *failed* source and returns `1` without ever confirming the prior SHA came back green. `scripts/deploy-hook.sh` records `PREV=$(git rev-parse HEAD)` **before** the reset, and on health-gate failure: `git reset --hard "$PREV"` → `docker compose -f docker-compose.yml -f docker-compose.prod.yml build --parallel` → `up -d` → **re-gate** to confirm the prior SHA is healthy again, then exit non-zero so the receiver logs a failed deploy. The build invocation uses **no `build … || build …` fallback** — that live-dispatcher pattern (`challenge-P2.md §2.2` defect 2) defeats `set -e` (the `||` makes the compound succeed on a failed primary build, so control falls through to `up -d` with a half-built image set). `scripts/deploy-hook.sh` preserves `set -euo pipefail` (the one `deploy.sh:4` discipline worth keeping) so a partial build aborts before `up -d` and the live stack is untouched (`R-deploy-spec §6` "Partial build" — falsified on the host, honoured here).

4. **Dirty-tree-fail-loud (C7) — the host fourier tree is DIRTY + stale.** The host `git -C /var/www/fourier-analysis status --porcelain` (read-only, `challenge-P2.md §3.1`) showed `M docker-compose.prod.yml`, `M docker-compose.yml`, `?? ssl/`. A blind `git reset --hard origin/master` (the first line of the live deploy) would **silently discard the modified tracked compose files** — which may carry host-specific overrides (the W2 TLS work, a port/secret tweak applied out-of-band) — with no warning and no record. `scripts/deploy-hook.sh` must therefore **check the working tree before any reset** and, on a dirty tree, **fail loud** (non-zero exit + a clear message naming the dirty paths) or stash-with-alert — never a silent `reset --hard`. (`ssl/` survives — `reset --hard` spares untracked files — but the modified *tracked* compose files do not.) This is recorded as a deploy-hook safety clause (synthesis `§2 C7`).

**Last-known-GREEN nuance (noted, bounded):** `R-deploy-spec §4`'s `PREV=$(git rev-parse HEAD)` is "the previously-checked-out SHA," which is last-known-good *only if the prior deploy was itself gated-green* — and fourier has never deployed through this chain, so the very first `$PREV` is the stale host SHA (`challenge-P2.md §2.1`). W1's deploy-hook records the **green** SHA on each successful gate (a tracked-out-of-tree marker, e.g. a host-side `last-green` file the script reads/writes) so the *second* and subsequent rollbacks pin last-known-green rather than bare `HEAD`. For the **first** deploy, the dirty-tree-fail-loud clause (improvement 4) forces the operator to reconcile the host tree before the first gated deploy, so the first `$PREV` baseline is reproducible. This is the honest answer to the `$PREV`-builds hazard (`challenge-P2.md §2.1`), not a claim that rollback is infallible.

`scripts/deploy-hook.sh` carries **no secret** (the only secret-bearing artefact is the host's `hooks.json`, Stratum B) and **no SSH** (it runs *on* the target, invoked by the host receiver). It is reviewable, versioned, and greppable — the proof that the deploy logic stays in fourier's chain.

### §2.3 — The honest scoped `8091` grep (C8)

The gate is **`git grep -nE '[:/]8091' -- ':!docs/*' ':!*.lock' ':!**/*.json'` → zero**, **not** the bare `git grep -n 8091 → zero` that `R-deploy-spec §8.2` asserts. The bare form is **provably unachievable** even after `deploy.sh` is deleted (`challenge-P2.md §6`, measured live): `8091` appears as an incidental substring in `uv.lock` (2 hits, inside `sha256:` hashes / PyPI URLs) and in seven committed curve-path JSON assets under `web/src/assets/fourier-paths/` (`8091` as a digit run inside floating-point coordinates), plus extensive `docs/**` prose discussing the bug. The bare grep returns **62 hits today** (measured) and cannot go to zero. The scoped form excludes docs, lockfiles, and JSON, and anchors on a port-reference (`[:/]8091`) so incidental digits do not match. **Measured behaviour:** today this scoped grep isolates *exactly* `scripts/deploy.sh:38,39` (the two real bug sites); after the §2.2 deletion it returns zero. `C.md §6` already corrects to this form.

### §2.4 — `docs/precepts/infra/` deploy note (created at W1 — lands FIRST)

W1 **creates** `docs/precepts/infra/` with a deploy note. It lands at W1 (W2 later adds `tls.md` per `C.md §3` W2 row). **Critical seam (C, `challenge-P2.md §7`): `docs/precepts/` is a git SUBMODULE** (`git submodule status` → `f27627e… docs/precepts`, confirmed live). A commit "documenting the host artefacts in `docs/precepts/infra/`" lands in the **precepts submodule's history**, not fourier's — fourier records only a gitlink bump, so `FINAL.md` (which lives in fourier) would cite a path outside fourier's chain. **W1 must therefore either** (a) author the deploy note inside the submodule, commit it there, bump the fourier gitlink, and cite **both** repos in the close record; **or** (b) author the deploy note at a fourier-tracked path (e.g. `docs/tranches/C/`) and have the precepts entry be a thin pointer. Stratum A's binding requirement is that the note's *content* is reachable from fourier's commit chain — the submodule boundary must be handled explicitly, not assumed away.

The deploy note records (never the secret itself):
- **Host-artefact locations**: `/usr/local/bin/webhook` (binary), `/opt/deploy/hooks.json` (hook registration), `/opt/deploy/scripts/dispatch.sh` (the shared dispatcher), `/opt/deploy/.env`, the `webhook.service` systemd unit, `command-working-directory: /opt/deploy`, the deploy target `/var/www/fourier-analysis`.
- **Secret discipline**: the HMAC secret lives only in (a) GitHub repo → Settings → Webhooks, and (b) the host `hooks.json`. It is **never in fourier's tree, never in `docker-compose*.yml`, never in `.env.example`** — verified clean (`challenge-P2.md §4`: `.env.example` carries only `MONGO_*`, `ADMIN_TOKEN=dev`, ports, VITE args; `git grep -lE 'hooks\.json|webhook\.service|adnanh|payload-hmac'` over the non-doc tree returns nothing). The `${VAR:?}` convention for `MONGO_PASSWORD` (`docker-compose.prod.yml:8,44,51`) is the in-tree secret-handling pattern (`W0-baseline.md §1.3`) and is recorded here too.
- **The measured secret-hygiene weakness as a recorded finding (NOT a Stratum-A fix)**: the host `hooks.json` + `/opt/deploy/.env` are `0664 mbabb:mbabb` — world-readable, not root-`0600` (`challenge-P2.md §4`). The greenfield spec asserted `0600`-root; the live reality is looser. Any local host user can read the secret and forge `X-Hub-Signature-256`. This is a **host-ops residual** (Stratum B) — recorded in the deploy note as the accepted-or-to-be-hardened posture, not silently claimed fixed.

## §3 — Stratum B: host-ops residual — proposed, NOT landed unilaterally (C6)

These touch the **shared** `/opt/deploy/dispatch.sh`, which serves four sibling repos (`words`, `speedtest`, `value.js`, `csp-solver`). W1 **cannot rewrite shared infra unilaterally** from fourier's tree without risking those four repos (synthesis `§2 C6`; `C.md §3` W1 row "proposed, not landed unilaterally"). W1 **proposes** the changes and carries them as a named host-ops residual to `coordination/`.

The proposal (what host wiring would entail, if performed):
- **Register / re-point fourier's hook arm** so `/opt/deploy/hooks.json`'s fourier `case` invokes the tracked `scripts/deploy-hook.sh` (Stratum A) rather than the inline dispatcher logic. The arm already exists (`challenge-P2.md §1.1`); pointing it at the repo-local script is the minimal wiring.
- **Shared-dispatcher hardening proposal** (touches all five repos — proposed, not imposed): adopt `flock` per-repo lockfiles in the shared dispatcher; replace the `build … || build …` fallback that defeats `set -e`; add rebuild + re-gate to the rollback path; harden `hooks.json` + `.env` to `0600`/root or document the accepted weaker posture. These mirror the Stratum-A improvements but at the shared layer — and rewriting them is **arguably its own constellation-level coordination** (synthesis `§2 C6`), not a fourier-W1 unilateral edit.
- **Reconcile the dirty host tree** (`M` on both compose files, stale SHA — `challenge-P2.md §3.1`) **before the first gated deploy**, or the `$PREV` baseline is unreproducible (C7). This is a host-ops step, surfaced loud by the Stratum-A deploy-hook's dirty-tree clause.

**The disposition rule (binding, `C.md §3` W1 row + synthesis `§2 C6`):**
- **IFF host wiring is performed this wave**, W1 records the **deploy-chain transcript** (a real push → receiver-verified-HMAC → on-host `scripts/deploy-hook.sh` run → green `8100` gate → logged `PREV → NEW` SHA pair, captured from `/opt/deploy/logs/mkbabb-fourier-analysis-*.log` or journald) **and** the **intentional-bad-commit rollback transcript** (push a commit that breaks startup — e.g. a syntax error in `api/main.py` so `/api/health` never returns `{"status":"ok"}` on `8100` — observe the gate fail, the `reset --hard $PREV` fire, the prior SHA rebuild + re-gate, the site stay up on last-known-good; then push the fix and observe a clean green deploy). These are the gates of `C.md §6` ("recorded commit-to-deploy chain") and `C.md §3` W1 ("rollback verified by an intentional bad commit").
- **ELSE** (host wiring deferred to a coordinated host-ops step), the close record reads **"repo-local landed, host-activation pending"** with the host residual carried to `coordination/`. The chain is **never claimed proven when it is not** (`C.md §6` invalid-gate: "'webhook configured' without a recorded deploy chain" is rejected at challenge). Note (`challenge-P2.md §2.3`): a transcript captured *before* the shared dispatcher is brought to spec would document the live dispatcher's *weaker* rollback (no rebuild, no re-gate) — so a transcript is only valid evidence of the spec's contract once the fourier arm invokes the Stratum-A `scripts/deploy-hook.sh`.

## §6 — What is OUT of scope (KISS / invariant 12)

- **No new container** (`R-deploy-spec §9`; `C.md §3` W1 row). The receiver is the existing host binary `/usr/local/bin/webhook`; W1 adds zero containers. A receiver inside the compose stack it tears down cannot survive its own deploy.
- **No registry adopted.** Build-on-host from source is preserved (`deploy.sh:26` topology); the git SHA *is* the deployable artefact, so rollback is git-SHA-based, not image-tag-based (`R-deploy-spec §4`). No registry rollback path is introduced.
- **No multi-replica.** Invariant 19's single-replica constraint is preserved (`docker-compose.prod.yml:11` `replicas: 1`); W1 does not introduce horizontal scaling.
- **No webhook *framework* / no new language runtime / no database.** The deploy logic is one shell script (`scripts/deploy-hook.sh`), not a pipeline DSL or a CI service (the `CA6`/inv-16 guard).
- **No unilateral rewrite of the shared `/opt/deploy/dispatch.sh`** (C6). It serves four sibling repos; the rewrite is proposed in `coordination/`, not landed from fourier's tree. This is the load-bearing scope boundary that distinguishes W1's honest landing from the greenfield spec's overreach.
- **No TLS work** — `tlsAllowInvalidCertificates` removal + the verified-cert issuer + the port-map ratification are **W2** (`C.md §3` W2 row). W1 lands the pipeline so W2's TLS change ships through it.
- **No host secret-permission *fix*** as a Stratum-A deliverable — the `0664` `hooks.json`/`.env` weakness is **recorded** (§2.4) and **proposed** as host-ops (Stratum B), not chmod'd from fourier's tree.
- **No force-push guard.** A force-push to `master` deploys the rewritten tree (no branch-protection in the trigger rule, `challenge-P2.md §5`); W1 **names this as a known property** (bounded, single-operator) in the deploy note, but does not build a guard against it.

## §7 — Failure-mode contract (each demonstrable iff host-wired; else the design is the artefact)

Per `R-deploy-spec §6`, corrected against the live findings (`challenge-P2.md §2.2`, `§3`):

| Mode | Required behaviour (in `scripts/deploy-hook.sh`) |
|---|---|
| Partial build | `set -euo pipefail` aborts before `up -d`; live stack unchanged; receiver logs non-zero. **No `build \|\| build` fallback** (the live-dispatcher defect that defeats `set -e`). |
| Health fail mid-deploy | rollback to `$PREV` with **rebuild + re-gate** (§2.1 improvement 3); site returns to last-known-good; exit non-zero. (The live dispatcher does `up -d` only — falsified; corrected here.) |
| Replay / duplicate webhook | HMAC rejects any *modified* payload (the live `payload-hmac-sha256` rule); an unmodified replay is idempotent (`reset --hard` to the same SHA + rebuild + no-op `up -d`); `flock` serialises concurrency (§2.1 improvement 1 — absent on the host today). |
| Two rapid pushes | `flock` serialises; the latest `HEAD` deploys once. |
| Dirty host tree | **fail loud** (non-zero + named dirty paths) before any `reset --hard` (§2.1 improvement 4, C7) — never the live dispatcher's silent discard. |
| Receiver crash | systemd `Restart=on-failure` respawns; an in-flight deploy recovers by re-push. (Host-ops; the unit already exists.) |
| Force-push to master | deploys the rewritten tree — named as a known property (§6), not guarded. |

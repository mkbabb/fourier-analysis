## Part A — janitor audit-log + recovery

### A.0 — The substrate (what already exists — do not re-engineer)

- The cycle `_cleanup_cycle` runs on startup and every six hours (`janitor.py:50-57`, the `run_janitor` `while True` loop with `asyncio.sleep(6 * 3600)` at `:57` and the `except Exception` swallow at `:55`). It performs **ten destructive ops in `janitor.py`** (nine `delete_many` + one `update_many` cascade-soft-delete at `:127`) and **one delegated destructive op** (the contour prune via `pinned_cron.cron_prune`, `janitor.py:95`), emitting **`logger.info` lines but zero audit rows**.
- An `admin_audit` collection **already exists** and is the canonical destination: the janitor itself prunes it (`janitor.py:168`), the admin router writes it on every moderation action via `log_audit` (`admin.py:72-81`), and the admin audit-viewer `list_audit` reads it (`admin.py:618-646`). **The schema is fixed, not novel** — W3 makes the janitor a *peer writer* into the same homogeneous collection.

### A.1 — The canonical row shape (mirror `log_audit`; do not invent columns)

`log_audit` (`admin.py:72-81`) inserts **exactly four fields**:

```python
{
    "timestamp": datetime.now(UTC),   # admin.py:76 — tz-aware UTC
    "ip_hash":   ip_hash,             # admin.py:77 — the admin actor's hashed IP
    "action":    action,             # admin.py:78 — e.g. "set_tier:featured"
    "target":    target,             # admin.py:79 — e.g. a slug, or "count=12"
}
```

The viewer model `AuditEntry` (`api/models/admin.py:92-96`) declares **all four required, none Optional**: `timestamp: datetime`, `action: str`, `target: str`, `ip_hash: str`. The viewer filters on `action` (exact, `admin.py:630-631`), `target` (regex, `admin.py:632-633`), and `timestamp` range (`admin.py:634-640`), and sorts on `timestamp` descending (`admin.py:646`).

**Homogeneity constraint (binding).** Janitor rows MUST satisfy `AuditEntry` — all four fields, same types — or the `/api/admin/audit` viewer (`admin.py:618`) fails to deserialise a mixed admin+janitor collection. This drives three reconciliations the implementer MUST follow verbatim:

1. **`ip_hash = "system:janitor"`** — a sentinel string constant. The janitor is not an IP-bearing actor; omitting the field breaks `AuditEntry`'s required `ip_hash: str` (`admin.py:96`), and widening the model to `str | None` would loosen the admin-action contract for the janitor's sake. The sentinel is a string (satisfies the model), self-documenting in the viewer, and trivially filterable. **This is the binding choice — do not omit, do not widen the model.**
2. **The structured payload (count, cutoff) lives in `target`.** `target` is already an opaque human-readable string carrying structured-ish payloads on the admin surface (`admin.py:443` `f"batch_visualizations:{body.action}"` and the like). The janitor follows the same convention: `target = f"count={n}, cutoff={iso}"` (the `cutoff=` clause omitted where a sweep has no cutoff bound, e.g. expired-sessions, which bounds on `now`).
3. **The sweep identity lives in `action`**, namespaced under a `janitor:` prefix so the whole janitor trail is one `?action`-prefix family disjoint from the admin actions, and exactly filterable via `admin.py:630-631`.

**Do NOT add new columns** (`category`, `count`, `cutoff` as separate top-level fields). The `C.md §3` phrase "(category, count, cutoff)" maps onto the *existing* four-field shape: **category ≡ the `janitor:` action namespace**, **count + cutoff ≡ the `target` payload**, **timestamp ≡ `timestamp`**. Adding columns makes janitor rows structurally divergent from admin rows — the rejected over-engineering (invariant 12).

```python
async def _log_janitor_audit(db, action: str, *, count: int, cutoff: datetime | None = None, **extra) -> None:
    if count < 1:                       # the count ≥ 1 gate, centralised
        return
    payload = f"count={count}"
    if cutoff is not None:
        payload += f", cutoff={cutoff.isoformat()}"
    for k, v in extra.items():          # e.g. users=…, images=…

    await db.admin_audit.insert_one(
        {
            "timestamp": datetime.now(UTC),
            "ip_hash": "system:janitor",   # the binding sentinel (A.1.1)
            "action": action,
            "target": payload,
        }
    )
```

One helper, eleven call-sites, the gate baked in. This keeps the diff small and the test's source-grep arm (§A.4) simple. The `datetime`/`UTC` imports already exist (`janitor.py:41`).

### A.3 — Partial-failure recovery (re-run idempotence — the guarantee to prove)

**The guarantee.** *The janitor cycle is idempotent under arbitrary mid-sweep death — re-running converges to the same end-state because every deletion is a `delete_many` over a live-state predicate, and audit rows never double-count because each row records exactly one `delete_many`'s return and a delete never re-removes a deleted document; the only failure mode is a single lost (never duplicated, never false) audit row when death falls between a delete and its record, which is fail-safe under-counting.*

**Why the deletions are already idempotent (confirm, do not re-engineer):**

- Every deletion filter is **time-bounded or flag-bounded against live state**, not against a checkpoint. `visualizations.delete_many({"deleted_at": {"$lt": grace_cutoff}})` (`:73`) deletes whatever currently matches; a re-run after a partial crash simply deletes the residual matches (already-deleted rows are gone and no longer match). `cron_prune`'s `{pinned: False, last_accessed_at: {$lt: cutoff}}` (`pinned_cron.py:39`) is identical in character. Expired sessions (`:113`), the stale-user cascades (`:127-163`, all `$in stale_slugs` where `stale_slugs` is **re-derived each cycle** from `last_seen_at` at `:120-121`), the audit prune (`:168`), the image prune (`:273`) — **all are `delete_many`/`update_many` over a predicate that re-evaluates against present state**. There is no "delete the rows I selected last time" cursor a crash could leave dangling. **A state-predicate delete is intrinsically idempotent.** Confirmed by the existing bounded-query test (`api/tests/test_janitor_bounded_query.py`).
- The pin recompute `_recompute_pin_flags` (`janitor.py:173-248`) is explicitly documented idempotent (`:188-191` — reset-then-`$merge`), so a crash between recompute and prune leaves the next cycle's recompute to re-establish the correct slate. **No special handling.**
- The one subtlety: the cascade chain (`:127`→`:139`→`:147`→`:155`→`:163`) is **not transactional** — a crash after the gallery cascade (`:139`) but before the user delete (`:163`) leaves the user document alive. **This is self-healing**: the next cycle re-derives `stale_slugs` from `last_seen_at` (which the partial run did not touch, `:120-121`), the still-stale user is re-selected, and the remaining cascades re-run against whatever survived. No orphan is created a later cycle cannot reap. **No saga / no compensation logic is warranted** (invariant 12) — the re-derivation IS the recovery. Confirm in Test 4.

**Why the audit rows do not double-count:**

The double-count hazard is *not* in re-running a sweep — it is in **writing an audit row for work a prior crashed run already wrote a row for**. The `count ≥ 1` gate of §A.2 resolves it directly:

- An audit row is written **immediately after** its `delete_many` returns, gated on `deleted_count ≥ 1`, recording **the count that this invocation deleted**. It is a *factual record of one delete operation*, not a cumulative tally.
- On a re-run after a partial crash, the re-run's `delete_many` deletes only the **residual** matches; it writes a row with the residual count, the prior run wrote a row with the partial count. **The two rows sum to the true total and neither is spurious** — each truthfully records the documents *that invocation* removed. No double-count, because each row is scoped to one `delete_many` return and a delete never re-removes a deleted document.
- The degenerate case — death *after* the `delete_many` succeeded but *before* the audit `insert_one` — loses exactly one audit row (the op happened, the record did not). This is an **acceptable, bounded, fail-safe loss**: under-counting the trail, never over-counting, never a false record. To make even this vanishingly improbable, **order the audit insert immediately after the delete in the same `await` sequence** — no intervening `await` that is a cancellation point (relevant under the §B reload-cancellation). Recording the row is `O(1)`; a two-phase / outbox pattern is **rejected** as gross over-engineering for a 6-hour background sweep (invariant 12).

## Part B — the `--reload` compute-abort fix

### B.1 — Diagnosis (mechanism-level, grounded)

**The invocation.** `scripts/dev.sh:73-76` launches the dev backend:

```bash
uv run uvicorn api.main:app \
    --host 0.0.0.0 --port "$API_PORT" \
    --reload --reload-dir api --reload-dir src        # dev.sh:74-76
```

With `--reload`, uvicorn runs a *supervisor* whose `watchfiles` watcher recursively monitors each `--reload-dir`. On a filesystem change under a watched directory, the supervisor **terminates the worker subprocess and spawns a fresh one**. The shutdown is not graceful with respect to in-flight CPU work — the worker process is replaced.

**The causal chain — why a `src/` write aborts an in-flight computation:**

1. The compute endpoints call into `api/services/computation.py`, which runs the heavy numerics **in a thread of the worker process** via `asyncio.to_thread(fn)` (`computation.py:43-44`, inside `submit_compute_job`), bounded by a semaphore (`:31-35`) and an `asyncio.wait_for(..., timeout=compute_timeout_s)` (`:43-46`).
2. That compute code lives in the **`fourier_analysis` package**, imported at `computation.py:12-15` (`fourier_analysis.bases / .contours / .epicycles / .shortest_tour`). The package is sourced from **`src/`** — `pyproject.toml` declares `packages = ["src/fourier_analysis"]`; the live tree is `src/fourier_analysis/`.
3. Therefore `--reload-dir src` watches **the exact tree whose code the compute thread is executing**. Any write under `src/` — an editor save, a formatter pass, a `git checkout` touching a `.py` — fires a `watchfiles` event.
4. The supervisor reacts by **killing the worker process**. Because the compute runs in a **thread of that same process** (not a separate process), killing the worker kills the thread mid-computation. The in-flight `to_thread` job is destroyed; the awaiting request never gets its `ComputeResult`. The `asyncio.wait_for` timeout guard (`computation.py:43-46`) **does not help** — the process is gone before the timeout fires.

**This is not a logic bug; it is the reloader working as designed on a watch scope that overlaps the compute library.** It is a *developer-ergonomics* finding (`W0-baseline.md §3`: "a developer-ergonomics fix, not a production correctness defect"), not a production correctness defect.

**Prod is unaffected — confirmed.** The production image runs `uvicorn … --workers ${WORKERS} --proxy-headers …` with **no `--reload`** (`api/Dockerfile:25`, the `production` stage `CMD`). There is no supervisor/watcher in prod; nothing kills the worker on a file event (and the prod filesystem is the immutable image). The **`development`** Dockerfile stage `CMD` *does* carry `--reload` but with **no `--reload-dir` narrowing** (`api/Dockerfile:16`: bare `--reload`), so it watches uvicorn's default — the app root, which under that `COPY . .` layout (`api/Dockerfile:15`) includes `src/`. **The dev container therefore has the same hazard as `dev.sh`.** The fix must address **both** dev surfaces to be a true root fix (`C.md §5` lists both `scripts/dev.sh` and `Dockerfile` under the W3 surface).

### B.2 — The chosen fix (KISS order (a) ⊳ (b) ⊳ (c) — chosen: (a))

**Chosen: (a) narrow the reload watch to exclude the compute path — `src/` comes off the watch entirely.**

**Rationale.** The point of `--reload-dir src` was to hot-reload the library during dev. But the library *is* the compute kernel — the very code whose in-flight execution the reload destroys. There is a genuine tension: watch `src/` for hot library reload but abort compute, or don't watch it so compute survives but a library edit needs a manual restart. **KISS resolves it decisively in favour of compute survival:**

- The backend's dev-loop job is to **serve the API** (compute + CRUD). High-frequency edits live in `api/` (routers, services, models) — `--reload-dir api` already covers them. The `src/` library (`fourier_analysis`) is the *stable numerical core*, edited far less often during API/web iteration; when it IS edited, a deliberate manual restart (Ctrl-C + re-run, or touch an `api/` file) is the honest low-cost signal.
- Watching `src/` actively **harms** the dev loop: a save in the library while an epicycle compute runs silently drops that request. The current default is strictly worse than not watching it.

**The fix, concretely (root, both surfaces — two one-line edits):**

| Surface | Site | Before | After |
|---|---|---|---|
| dev script | `scripts/dev.sh:76` | `--reload --reload-dir api --reload-dir src` | `--reload --reload-dir api` (drop the `--reload-dir src` token) |
| dev container | `api/Dockerfile:16` | `… "--port", "8000", "--reload"]` | `… "--port", "8000", "--reload", "--reload-dir", "api"]` |

The reloader now watches only the API surface; the compute library is stable across a compute run. The `production` stage (`api/Dockerfile:18-25`) is **untouched** — it has no `--reload` and is already correct. This is a **one-token deletion** in `dev.sh` and a **one-flag narrowing** in the dev Dockerfile stage. No new process, no new dependency, no queue — the smallest mechanism that holds invariant 12.

**Residual it leaves (named, accepted):** a `src/` library edit no longer hot-reloads — it needs a manual dev-server restart. This is the correct trade: the compute kernel is the thing whose edits *should* force a clean restart, and forcing it avoids the silent compute-abort. There is no scenario where dropping `src/` from the watch loses correctness; it only changes which edits trigger an automatic restart.

### B.3 — Rejected alternatives (recorded)

**(b) Scope compute off the reloaded process** (run the compute kernel in a separate, unwatched process). **Rejected as heavier than the problem.** It is genuine multi-process plumbing (a process pool or a worker subprocess + IPC of numpy arrays), adds serialization cost across the boundary, and complicates the `asyncio.wait_for` timeout + semaphore bookkeeping that currently lives cleanly in-process (`computation.py:29-53`). It does not even solve the stated dev pain ("my compute died when I saved a file") better than (a), which eliminates that at zero new infrastructure. (b) would only be warranted by a *production* process-isolation need — there is none (invariant 19 fixes single-replica; prod has no reload). **Deferred permanently unless a production process-isolation need arises.**

**(c) Route compute to a background task / queue** (Celery, arq, a Mongo-backed job table). **Rejected outright for this fix.** A background queue is a large operational surface (a broker or a polling worker, a job-state collection, result-fetch polling on the frontend, new failure modes) — exactly the "new container/dependency" `C.md §3`/Wχ.P1 require per-line justification to admit, and which invariant 12 forbids absent a real need. Answering a *developer-ergonomics* finding with a job queue is the textbook over-engineering the precepts forbid. The current in-process `asyncio.to_thread` + bounded semaphore + timeout (`computation.py:29-53`) is the right scale for a single-replica synchronous-result API where the client awaits its `ComputeResult` inline.

**(c) deferred to fourier-D with its explicit trigger.** *If* a future tranche needs compute that outlives a single request — minutes-long fits, multi-user fairness beyond the current `compute_concurrency` semaphore (`computation.py:25`), or compute results that must survive a deploy — *then* a background queue earns its surface. **That is a fourier-D concern, not C's.** Recorded here so the decision is auditable, not silently dropped. (Mirrors the `C.md §7` "fourier-D opens if ever needed" pattern for multi-replica.)

**Why not "make the reloader graceful" (non-option, for completeness).** uvicorn's reloader has no "drain in-flight compute before respawn" mode; even graceful HTTP shutdown does not wait on a detached `to_thread` CPU job. The only levers are *what to watch* (a) and *where compute runs* (b/c). (a) is the smallest correct lever.

## §1 — P1 storage conditions (→ W5 hard gates, binding)

The filesystem+nginx app-served choice survives every attack on the *choice* — the path-traversal probe correctly failed to land (`IMAGE_SLUG_PATTERN`, `dependencies.py:38`, `^[a-zA-Z0-9][-a-zA-Z0-9]{2,80}$`, admits no `.`/`/`/`%2e`), GridFS/MinIO/S3 were dismissed honestly, `FileResponse` is a genuine win. The "0 cost" accounting was the dishonest part. Four binding conditions:

- **C1 (BLOCKER) — the delete must stay coupled to the bytes.** `_delete_images_and_cascade` (`janitor.py:251-274`) deletes the Mongo doc + cascades gallery rows but **never unlinks the relocated file**. Post-W5 the volume grows unbounded — the relocation defeats invariant 18 ("bounded and observable footprint"). **W5 must extend the image-delete path to unlink `<blob_dir>/<slug>` + `<slug>.thumb` whenever it deletes an `images` doc** (the recency prune at `:251-274` AND the cascade-soft-delete-hard-delete paths). Verified by a test: delete an image → assert the file is gone.
- **C2 (BLOCKER) — volume ownership.** The backend runs as the unprivileged `app` user; a fresh named Docker volume is root-owned → `write_bytes` raises EACCES → the migration cannot run. **W5 must establish volume ownership** (an init step `chown`ing `blob_dir` to the app UID, or a tmpfs/`user:`-set mount). Confirm the exact Dockerfile path + app UID at W5 open (the P1 anchor `Dockerfile:23` must be re-confirmed — there is no repo-root `Dockerfile`; it is under the build context).
- **C3 (hardening) — path-confinement guard.** `_resolve()` must confine the resolved path under `blob_dir` (a `Path.resolve()` + `is_relative_to(blob_dir)` assertion), defence-in-depth behind the regex. The regex is the primary guard; this is the second layer so a future slug-validation regression cannot become an arbitrary-read.
- **C4 (documented cost) — backup/DR.** Inline-Mongo blobs were covered by `mongodump` for free; the relocated files are a **second durable surface** holding the *sole* copy of uploads post-cutover. W5 must document the backup story in `docs/precepts/infra/` (back up `image_blobs` alongside `mongo_data`; the two must restore consistently) and the prod volume must be `external: true` (or otherwise protected) so `docker compose down -v` cannot wipe it. This is invariant 18's "observable" clause made honest.

## §2 — P2 CI/CD conditions (→ W1 hard gates + a scope reconciliation, binding)

The R2 *direction* (HMAC-SHA256 payload auth, gated to `refs/heads/master`; dev-pushes/server-reacts; no new container; clean `deploy.sh` deletion proof) is sound. But R2 was written **greenfield against a host that already runs a contradicting design**. The reconciliation, not the greenfield spec, is what W1 lands.

- **C5 (SCOPE — the load-bearing reconciliation).** A live, operational, **multi-repo** `adnanh/webhook` dispatcher already exists on `mbabb.fridayinstitute.net`: `/opt/deploy/scripts/dispatch.sh`, `webhook` active on `*:9000`, `hooks.json` at `/opt/deploy/` (`0664 mbabb:mbabb`), serving **four sibling repos**. It contradicts R-deploy-spec on nearly every concrete clause (hooks path, file perms, bind address, no flock, rollback does `up -d` only with no rebuild/re-gate, a `build || build` fallback that defeats `set -e`). **fourier has never deployed through it** (zero fourier entries in its logs). **W1 must reconcile**: adopt the existing dispatcher's conventions for the fourier-repo-local artefacts (`scripts/deploy-hook.sh` matching the dispatcher's invocation contract), and treat changes to the *shared* dispatcher as host-ops that touch four other repos — **flagged as outward-facing, not landed unilaterally from this repo**. The greenfield `/etc/webhook/`+`root:0600`+loopback design is **rejected** as a fiction; the honest target is the existing `/opt/deploy/` reality, improved in place where fourier-local (the flock, the real health-gate, the rebuild-on-rollback) and proposed-not-imposed where shared.
- **C6 — what W1 can prove from this repo vs the host residual.** W1 **can** land + prove, repo-locally: the tracked `scripts/deploy-hook.sh` (matching the dispatcher contract, with `flock` + a real `:8100` health-gate + rebuild-on-rollback), the `scripts/deploy.sh` deletion proof, the `docs/precepts/infra/` deploy note recording where the host artefacts live + the secret discipline, and the honest `git grep` (see C8). W1 **cannot** unilaterally rewrite the shared `/opt/deploy/dispatch.sh` without risking four sibling repos — that is a **named host-ops residual** requiring an explicit, careful, out-of-band step (and arguably its own constellation-level coordination). The W1 close records the deploy-chain transcript **iff** the host wiring is performed; otherwise the chain is "spec + repo-local artefacts landed, host-activation pending" — recorded honestly, never claimed as proven-when-it-isn't (`C.md §6`: "'webhook configured' without a recorded deploy chain" is an invalid gate).
- **C7 — the dirty/stale host tree.** The host's fourier checkout carries uncommitted `M` on both compose files and sits on a stale SHA; a `git reset --hard origin/master` would silently discard them. W1's deploy-hook contract must surface (not silently discard) a dirty tree — fail-loud, or stash-with-alert — before the reset. Recorded as a deploy-hook safety clause.
- **C8 — the honest `8091` grep.** `git grep -n 8091` returns non-zero on incidental substrings (`uv.lock`, seven curve-path JSON assets) — the `C.md §6` / R2 gate "`git grep 8091` → zero" is **unachievable as written**. The honest form is `git grep -nE '[:/]8091' -- ':!docs/*' ':!*.lock' ':!**/*.json'` → zero (the port-reference form, excluding incidental digits). `C.md §6` corrects to this.

## §3 — P3 atomicity conditions (→ W5 hard gates; window struck WITH conditions)

The core atomicity proof **survives**: a single standalone `mongod` (`prod.yml` `replicas: 1`, no `--replSet`), a fresh `find_one` per request (`dependencies.py:47-55`, no app-side doc cache), default read concern ⇒ `blob` XOR `storage_uri` holds per-document at every instant, no stale-read hole. **The §8 brittleness window IS struck** — but only with these conditions bound into W5:

- **C9 (BLOCKER — the real bug) — the dedup-hit-on-migrated-doc path.** `store_image_asset`'s dedup branch (`image_storage.py:66-85`) reads `existing["blob"]` unconditionally (`:70-72`, subscript not `.get()`) to regenerate a thumbnail; on an already-migrated `blob`-less doc this raises `KeyError`, **swallowed by the broad `except Exception` at `:81`** → the thumbnail is silently not regenerated. It fires on *every* dedup upload after migration and has **zero test coverage**. Worse, the write-back at `:75-80` (`:77` `Binary(thumb_bytes)`) **re-inlines a thumbnail Binary** — re-violating invariant 18 on the converged collection. **W5 must (a) rewrite the dedup-hit read through the `image_bytes` shim, (b) rewrite the thumbnail write-back to store a file + `thumbnail_uri` (never an inline Binary), and (c) prove it with a new `test_dedup_hit_on_migrated_doc`.** Both fixes cut over in the same deletion-proof commit.
- **C10 — the compute-backfill projection.** `dependencies.py:91-100` projects `{blob:1}` (inclusion-mode) — post-migration this starves the shim of `storage_uri`. The rewrite must change the **projection** (drop `{blob:1}`, project the fields the shim needs), not just the read call. Named in the W5 rewrite list.
- **C11 — no "skip if file exists" optimization.** The crash-mid-`write_bytes` self-heal depends on the re-run *overwriting* (truncate-and-write) any `{blob exists, storage_uri absent}` doc's file. W5 must NOT add a "skip if file present" short-circuit — it would orphan a truncated partial file. Recorded as a migration-script constraint.
- **C12 — overlay path.** `images.py:159-200` (`…/overlay`, reads `image_bytes` at `:169`) is already shim-routed — confirmed covered, no extra work, listed so it is not forgotten.
